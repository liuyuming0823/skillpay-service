# 接入教程：从零到收到第一笔钱

这份教程假设你拿到了本源码包，目标是**让你的服务能按次收费**。
全程分六个阶段，前两个阶段不需要任何支付宝账号，可以立刻开始。

---

## 0. 开始之前

### 你会得到什么

一个自托管的支付服务：任何客户端（AI 智能体、桌面程序、脚本）请求你的付费资源时，
服务端返回 HTTP 402 与账单；客户端付款后带着凭据回来，服务端验付、落库、把你准备好的东西交出去。

### 前置条件

| 项目 | 要求 |
|---|---|
| 开发机 | 能装 .NET SDK 10（Windows / macOS / Linux 均可） |
| 服务器 | 1 核 1G 起，公网 IP，Linux（Ubuntu 22.04 实测可用） |
| 支付宝 | 企业或个人支付宝账号，用于开放平台签约 |
| 域名 | **可选**。只用 IP + HTTP 也能跑通，详见第 5 阶段 |

### 时间预期

| 阶段 | 内容 | 耗时 |
|---|---|---|
| 1 | 支付宝侧开通与签约 | 1–3 个工作日（卡在审核） |
| 2 | 本机跑通 | 30 分钟 |
| 3 | 配置你的商品 | 10 分钟 |
| 4 | 部署上线 | 30 分钟 |
| 5 | 真实付款验证 | 15 分钟 |
| 6 | 客户端对接 | 视情况 |

**建议顺序**：先做阶段 2（不需要等审核），把链路摸熟；同时提交阶段 1 的签约申请。

## 1. 全流程地图

```
┌─────────────┐  ①请求付费资源   ┌──────────────────┐
│  客户端      │ ───────────────> │  SkillPay 服务    │
│ (AI/程序)    │                  │  (你的服务器)      │
│             │ <─────────────── │                  │
│             │  ②402 + 账单      │  ③创建待支付订单   │
│             │                  │   并落库          │
│  ④用户付款   │                  └──────────────────┘
│  (扫码/授权)  │                            ▲
│             │  ⑤带 Payment-Proof 重试       │
│             │ ────────────────────────────>│
│             │                  ┌──────────────────┐
│             │                  │ ⑥向支付宝验付     │
│             │                  │ ⑦校验本地订单     │
│             │                  │ ⑧交付并落库       │
│             │ <─────────────── │                  │
└─────────────┘  ⑨200 + 交付物    └──────────────────┘
```

三个关键认识：

1. **服务端不主动推送**。支付宝不会回调你的服务；是客户端带着凭据回来，你的服务再去问支付宝「这笔钱到了吗」。
2. **订单必须落库**。服务端在发出账单前就写下待支付订单，否则用户付了钱你无法对账。
3. **交付与连接脱钩**。履约一旦开始，客户端断开也不会中断，用同一个凭据重试就能取回结果。

## 2. 第 1 阶段：支付宝侧开通

> 这一阶段的操作都在网页上进行，页面可能随版本调整，**以平台实际页面为准**。
> 核心是三件事：拿到 **APPID**、拿到 **密钥对**、拿到 **serviceId**。

### 2.1 创建应用，拿到 APPID

1. 登录 [支付宝开放平台](https://open.alipay.com/)，进入「控制台」。
2. 创建应用（网页/移动应用均可）。创建完成后在应用详情页能看到 **APPID**（16 位数字）。
3. 把 APPID 记下来，稍后填进配置的 `Alipay:Aipay:AppId`。

### 2.2 生成密钥对（重点，容易踩坑）

在应用详情页找到「开发设置 → 接口加签方式」，选择 **公钥模式**，按引导生成密钥。

**关键点：支付宝密钥工具的「生成密钥」默认产出 PKCS#8（给 Java 用的）。**
本服务用的 .NET SDK **只接受 PKCS#1**，必须再做一次格式转换。

| 步骤 | 操作 |
|---|---|
| 1 | 用密钥工具生成密钥对，得到「应用私钥」与「应用公钥」 |
| 2 | 用工具里的「**格式转换**」把应用私钥从 PKCS#8 转为 **PKCS#1** |
| 3 | 把**应用公钥**粘贴到开放平台保存 |
| 4 | 从开放平台下载/复制**支付宝公钥** |

最后你会拿到三样东西：

| 名称 | 用途 | 敏感度 |
|---|---|---|
| 应用私钥（PKCS#1） | 你的服务给账单签名 | **绝密**，只留在服务器 |
| 应用公钥 | 交给支付宝，让支付宝验证你的签名 | 公开 |
| 支付宝公钥 | 你的服务用来验证支付宝的应答 | 公开 |

> 如果忘了转换格式，服务**启动时就会失败**并提示：
> `PrivateKey 是 PKCS#8 格式，而支付宝 .NET SDK 只接受 PKCS#1`。
> 这是刻意设计——比等到第一笔真实付款才报错要好得多。

### 2.3 签约并创建服务，拿到 serviceId

1. 在开放平台签约「**AI 付 / 按量付费**」相关的产品能力。
2. 在**服务市场**创建一个服务，登记你的服务信息：
   - **服务地址**：填 `http://<你的公网IP>/v1/skills/result`
     （统一入口，以后新增商品不用再来改地址）
   - **服务单价**：**必须与你配置文件里的 `Price` 完全一致**，否则用户无法支付
3. 创建成功后拿到 **serviceId**，形如一串大写字母数字组合。填进配置的 `Alipay:Aipay:ServiceId`。

同时记下你的**商户 PID**（`2088` 开头）与**商户名称**（会显示在用户的支付账单上）。

### 2.4 把生产网关切换过来

配置文件里默认是**沙箱网关**。签约生效后，把网关改成生产网关：

```
https://openapi.alipay.com/gateway.do
```

> 安全检查：如果网关指向生产，但 `ServiceId` 还是 `api_mock_service_id`，
> 服务会**拒绝启动**。这是上线前最常见的事故，已经在代码里堵住。

## 3. 第 2 阶段：本机跑通（不需要支付宝账号）

源码包里自带一对**自签的测试密钥**，配合沙箱配置可以直接在本机跑通完整 402 链路。

> 这对密钥在 `appsettings.Development.json` 里，它**只用于本机联调**，
> 与任何真实支付宝账号无关，也无法用于真实收款。

### 3.1 编译

```bash
cd skillpay-service
dotnet build
```

期望输出 `0 个警告 0 个错误`。

### 3.2 启动

```bash
# Windows PowerShell
$env:ASPNETCORE_ENVIRONMENT="Development"
$env:ASPNETCORE_URLS="http://127.0.0.1:18080"
dotnet bin/Debug/net10.0/SkillPay.Service.dll

# Linux / macOS
export ASPNETCORE_ENVIRONMENT=Development
export ASPNETCORE_URLS="http://127.0.0.1:18080"
dotnet bin/Debug/net10.0/SkillPay.Service.dll
```

启动日志里会打印三行关键信息，确认它们正常：

```
skillpay-service 启动：网关=https://openapi-sandbox... appId=2021000000000000 ... 
订单存储：/.../appdata/skillpay.db；已上架资源 2 个：demo-skill, demo-file
资源交付：文件根目录=payloads 履约时限=600秒 内联上限=8388608字节
```

### 3.3 手工验证 402

```bash
curl -i "http://127.0.0.1:18080/v1/skills/demo-skill/result"
```

期望：`HTTP/1.1 402 Payment Required`，响应头带 `Payment-Needed`。

把它解码出来看账单长什么样：

```bash
curl -s -D - -o /dev/null "http://127.0.0.1:18080/v1/skills/demo-skill/result" \
  | grep -i '^payment-needed' | cut -d' ' -f2 \
  | tr '_-' '/+' | base64 -d 2>/dev/null | python3 -m json.tool
```

你会看到 `protocol` 与 `method` 两个节点，以及 8 个签名字段。

### 3.4 跑联调脚本

```bash
node scripts/smoke-test.mjs
```

期望：`合计 18 项，通过 18 项，失败 0 项。`

**这一步非常重要**——它包含一个**独立复现的 RSA2 验签**：
用配置里的公钥在 Node 侧重新验证服务端给出的签名。
如果这里通过，说明你的签名实现是对的，后面真实付款就不会卡在「验签失败」上。

## 4. 第 3 阶段：配置你要卖的东西

### 4.1 决定交付形态

| 你要卖的东西 | 用哪种 | 配置字段 |
|---|---|---|
| 源码包、安装包、数据集、报告 | 文件交付 | `PayloadFile` |
| 授权码、简短说明、提示词 | 文本交付 | `PayloadText` |
| 需要现场生成（调大模型等） | 改造代码 | 见 4.4 |

### 4.2 卖一个文件（最常见）

1. 把你的文件放进 `payloads/`：

```
payloads/
└── my-source-code.zip
```

2. 在 `appsettings.json` 的 `SkillCatalog:Skills` 下新增一条：

```jsonc
"my-source-code": {
  "Price": "29.90",
  "GoodsName": "我的源码包",
  "Description": "含完整源码与接入文档",
  "PayloadFile": "my-source-code.zip",
  "PayloadFileName": "my-source-code.zip",
  "PayloadMimeType": "application/zip"
}
```

3. 重启服务，访问 `GET /` 确认新商品出现在目录里，且 `payload_configured` 为 `true`。

### 4.3 三个必须一致的数

**这是最常见的付款失败原因**，务必逐一核对：

| 位置 | 值 | 说明 |
|---|---|---|
| `appsettings.json` 的 `Price` | `29.90` | 服务端下发的账单金额 |
| 支付宝服务市场登记的「服务单价」 | `29.90` | 平台侧登记的单价 |
| 客户端/技能标价 | `29.90` | 用户看到的价 |

三者必须**完全一致**。任何一处不同，用户付款时都会被拒。

### 4.4 需要现场生成的交付物

如果你想在付款后现场生成内容（而不是交付现成文件），改造点在
`Services/PaidResourceFactory.cs` 的 `CreateAsync`：

```csharp
public async Task<string> CreateAsync(
    string resourceId, string outTradeNo, string skillCode,
    string? inputJson, CancellationToken cancellationToken)
{
    SkillDefinition definition = _catalog.Value.Resolve(skillCode) ?? throw ...;

    // 在这里接入你自己的生成逻辑，返回 JSON 字符串
    // inputJson 是客户端的原始请求体，可用来读取参数
    ...
}
```

要点：

- **必须对同一订单稳定**。同一订单重试时会复用已落库的产出，
  但如果首次生成失败要重试，你的逻辑应当是确定性的（或把随机种子绑定到 `outTradeNo`）。
- **把耗时算进 `Delivery:FulfillmentTimeoutSeconds`**。默认 600 秒。
- **生成在事务外进行**。仓储层已经是「只读校验 → 事务外生成 → 短事务落库」，
  不要在生成逻辑里开数据库事务，否则会长时间锁定 SQLite。
- **失败要抛异常，不要返回空**。抛出会让订单保持未履约状态，用户可以重试；
  返回空内容会被判定为履约失败。

## 5. 第 4 阶段：部署上线

### 5.1 服务器准备

```bash
# Ubuntu 22.04 示例：安装 ASP.NET Core 运行时与 SDK（SDK 用于在服务器上编译发布）
# 版本按你的实际系统选择，参考微软官方文档
sudo apt-get update
sudo apt-get install -y dotnet-runtime-10.0 dotnet-sdk-10.0 nginx git

# 目录规划
sudo mkdir -p /opt/skillpay /var/log/skillpay
```

### 5.2 拉代码

```bash
# 把源码包上传到服务器后解压，或推到自己的 git 仓库再 clone
sudo git clone <你的仓库地址> /opt/skillpay/src
# 或：sudo unzip skillpay-service.zip -d /opt/skillpay/src
```

### 5.3 写生产配置

复制模板并填写：

```bash
sudo cp /opt/skillpay/src/appsettings.Production.json.example \
        /opt/skillpay/app/appsettings.Production.json   # 稍后由部署脚本创建 app 目录
```

> 更推荐的做法：**私钥用环境变量注入**，不写进文件。
> 见 5.6 的 systemd 环境文件写法。

### 5.4 首次部署

```bash
cd /opt/skillpay/src
sudo bash deploy/deploy.sh
```

脚本会依次：拉最新代码 → 发布到 `/opt/skillpay/app` → 安装 systemd 单元 →
重启服务 → 健康检查。看到 `OK healthz:` 就成功了。

### 5.5 配置 nginx 反向代理

```bash
sudo cp /opt/skillpay/src/deploy/nginx-skillpay.conf /etc/nginx/sites-available/skillpay
sudo ln -sf /etc/nginx/sites-available/skillpay /etc/nginx/sites-enabled/skillpay
sudo rm -f /etc/nginx/sites-enabled/default
sudo nginx -t && sudo systemctl reload nginx
```

验证：

```bash
curl http://<你的公网IP>/healthz
# → {"status":"ok","database":"reachable",...}
```

### 5.6 用环境变量注入密钥（推荐）

把敏感值放进一个只有 root 能读的文件，通过 systemd drop-in 加载：

```bash
sudo -i
install -d -m 700 /etc/skillpay

cat > /etc/skillpay/llm.env <<'EOF'
ALIPAY_APP_ID=2021xxxxxxxxxxxx
ALIPAY_PRIVATE_KEY=<PKCS#1 纯 Base64，单行>
ALIPAY_PUBLIC_KEY=<支付宝公钥>
ALIPAY_SELLER_ID=2088xxxxxxxxxxxx
ALIPAY_SELLER_NAME=<商户名>
ALIPAY_SERVICE_ID=<真实 serviceId>
ALIPAY_GATEWAY=https://openapi.alipay.com/gateway.do
EOF

chmod 600 /etc/skillpay/llm.env
install -d /etc/systemd/system/skillpay.service.d
printf '[Service]\nEnvironmentFile=-/etc/skillpay/llm.env\n' \
  > /etc/systemd/system/skillpay.service.d/llm.conf
systemctl daemon-reload && systemctl restart skillpay
systemctl is-active skillpay
```

最后一行应输出 `active`。

> **为什么用独立环境文件而不是直接改 unit**：`deploy.sh` 每次部署都会重装
> `/etc/systemd/system/skillpay.service`，写在 unit 里的环境变量会被覆盖；
> 而 `skillpay.service.d/` 下的 drop-in 不会被覆盖，且与配置文件分离，便于轮换密钥。
>
> 另外注意：用 `printf` 而不是 `echo`，避免 `echo` 对反斜杠的转义处理带来意外。

### 5.7 关于域名与 HTTPS（收款前提，不是可选项）

> ⚠️ **资源地址必须是 HTTPS。** 支付宝官方 CLI（`alipay-bot`）会硬性拒绝 HTTP 资源地址，
> 直接报 `Error: paid resource URL must use HTTPS`。也就是说 **IP + HTTP 只能签发账单、收不到钱**——
> 买家连支付入口都生成不出来，账单签得再正常也没用。
> 下面三条路任选其一，但**必须走到 HTTPS** 才开始真实收款。

| 方案 | 耗时 | 需要备案 | 说明 |
|---|---|---|---|
| **Cloudflare 隧道**（建议先用它跑通） | 几分钟 | **不需要** | 由服务器主动出站连 Cloudflare，不走境内 80/443 入站，因此不触发备案拦截。先用临时隧道验证收款，再换固定域名 |
| 香港 / 境外地域实例 + 域名 | 1 天左右 | 不需要 | 需另开机器，可正常申请免费证书 |
| 大陆地域 + 自有域名 + 备案 | 7–20 天 | 需要 | 最正规；等待期间可用隧道顶着 |

补充：**在中国大陆地域的云服务器上，用任意域名访问 80 端口都会被强制 302 到备案提示页**
（与该域名是否真实存在无关），裸 IP 不受影响。

#### 用 Cloudflare 隧道当天拿到 HTTPS

```bash
# 1) 装 cloudflared（GitHub 直连不通时用下面的镜像）
mkdir -p ~/.local/bin
curl -fsSL --connect-timeout 10 -m 180 -o ~/.local/bin/cloudflared \
  "https://ghfast.top/https://github.com/cloudflare/cloudflared/releases/latest/download/cloudflared-linux-amd64" \
  && chmod +x ~/.local/bin/cloudflared && ~/.local/bin/cloudflared --version

# 2) 起隧道，直接指后端端口（绕开 nginx，不用管它监听在 80）
setsid nohup ~/.local/bin/cloudflared tunnel --url http://127.0.0.1:18080 > ~/cf.log 2>&1 < /dev/null &
sleep 20
grep -oE 'https://[a-zA-Z0-9._-]+\.trycloudflare\.com' ~/cf.log | head -1

# 3) 自检：期望 402
curl -s -o /dev/null -w '%{http_code}\n' https://<上一步拿到的地址>/v1/skills/<你的资源编码>/result
```

隧道的三条纪律：

- **必须用 `setsid nohup` 起在后台**。前台跑的话 SSH 空闲超时一断隧道就死、地址作废：
  付款**前**断 = 钱货两空；付款**后**断 = 重开隧道换地址，用**同一凭据**重取即可，钱不会丢。
- **快速隧道地址随进程变化**，只能用于验证，不要写进技能。长期售卖请买域名后建 named tunnel 拿固定地址。
- **经 Cloudflare 后响应头会变成小写** `payment-needed`，取账单时 `grep` 记得加 `-i`。

走域名 + 证书路线时，`deploy/nginx-skillpay.conf` 底部已备好 HTTPS 配置块：放好证书、取消注释、
改 `server_name`，`nginx -t && systemctl reload nginx` 即可。
（本机 nginx 若为 1.18，TLS 参数要写在 `listen` 行内，不支持新式 `http2 on;`）

### 5.8 上线后：把 HTTPS 地址同步回技能（最容易漏的一步）

拿到 HTTPS 地址只完成了一半。**买家装到的技能里写死了资源地址**，不同步的话买家打出去的仍是旧地址，
照样付不了款。需要改两处：

| 位置 | 改什么 |
|---|---|
| 技能 `SKILL.md` 的商品信息表 | 「资源地址」一栏 |
| 客户端脚本里的默认地址常量 | 例如 `DEFAULT_RESOURCE_URL` / `RESOURCE_URL` |

改完重新发布技能。若脚本支持环境变量（如 `PAY_SERVICE_RESOURCE_URL`），临时验证时可先用它覆盖，
但正式发布必须改代码里的默认值。

改地址时的两条纪律：

- **地址可以变，凭据不能丢**：已付款的买家换地址后，用**同一个** `Payment-Proof` 重试即可取货，
  服务端幂等，不会重复扣费。
- **每次改完都自检一次**：`curl` 打资源地址期望 402，再真实付一笔验证交付物 SHA-256 一致。

## 6. 第 5 阶段：真实付款验证

上线后**务必自己真实付一笔**，把整条链路走通再对外开放。

### 6.1 确认账单可下发

```bash
curl -i "http://<你的公网IP>/v1/skills/my-source-code/result"
# → 402 + Payment-Needed
```

### 6.2 完成一笔支付

用你配置的客户端（或支持 AI 付的支付工具）发起支付。典型流程：

1. 客户端请求付费端点，拿到 402 与账单；
2. 客户端解析 `Payment-Needed`（Base64URL 解码），展示金额与商户名；
3. 用户确认支付（扫码或其他方式）；
4. 客户端拿到 `Payment-Proof`，**用同一请求体重试原请求**。

> ⚠️ **必须原样重发同一请求体**。账单里不包含请求体内容，服务端验付时也无法知道
> 客户端第一次发了什么。如果重试时换了参数，会出现「付 A 的钱、拿 B 的货」。

### 6.3 验证交付结果

成功后响应形如：

```json
{
  "resource_id": "skillpay:my-source-code",
  "content": "{\"status\":\"success\",\"delivery\":{...}}",
  "trade_no": "20260917...",
  "out_trade_no": "SP20260917...",
  "fulfillment_confirmed": true
}
```

检查三件事：

1. `fulfillment_confirmed` 为 `true`
2. `content` 解析后 `delivery.type` 是 `file_base64` 或 `text`
3. `trade_no` 与支付宝里那笔交易号一致

### 6.4 验证幂等（重要）

用**同一个 `Payment-Proof`** 再请求一次。期望：

- 返回 200，内容与上次完全相同
- `already_fulfilled` 为 `true`
- **不会重复扣费**

这是幂等履约的设计目标：用户不会因为客户端重试而被收两次钱。

## 7. 第 6 阶段：客户端对接

你的客户端（技能/Agent/程序）需要做四件事。

### 7.1 最小客户端（Node.js）

完整可运行示例见 `examples/client-sample.mjs`。核心逻辑：

```js
const RESOURCE = 'http://<你的服务地址>/v1/skills/my-source-code/result';

// ① 首次请求 → 402
let res = await fetch(RESOURCE);
if (res.status === 402) {
  const bill = JSON.parse(
    Buffer.from(res.headers.get('payment-needed')
      .replace(/-/g, '+').replace(/_/g, '/'), 'base64').toString('utf8')
  );
  console.log(`需支付 ${bill.protocol.amount} ${bill.protocol.currency}`);
  console.log(`收款方 ${bill.method.seller_name}`);
  // ② 在这里完成支付，拿到 paymentProof
}

// ③ 带凭据重试
res = await fetch(RESOURCE, { headers: { 'Payment-Proof': paymentProof } });

// ④ 解析两层 JSON
if (res.status === 200) {
  const outer = await res.json();
  const inner = JSON.parse(outer.content);      // 注意：content 是字符串
  const d = inner.delivery;

  if (d.type === 'file_base64') {
    const buf = Buffer.from(d.content_base64, 'base64');
    fs.writeFileSync(d.file_name, buf);
    // 校验完整性
    const sha = crypto.createHash('sha256').update(buf).digest('hex');
    if (sha !== d.sha256) throw new Error('交付文件校验失败');
  } else if (d.type === 'text') {
    fs.writeFileSync(d.file_name, d.content, 'utf8');
  }
}
```

### 7.2 客户端必须处理的四种响应

| 状态码 | 含义 | 客户端动作 |
|---|---|---|
| 402 | 需要支付 / 凭据无效 | 取 `Payment-Needed` 发起支付，然后重试 |
| 200 | 交付成功 | 解析并落盘，校验 `sha256` |
| 400 | 资源编码非法 | 检查配置，不要重试 |
| 404 | 资源未上架 | 检查服务端目录配置 |
| 500/502 | 服务端错误 | **保留凭据**，稍后用同一凭据重试 |

> 特别提醒：402 也用于「凭据无效」的场景（而不是返回 5xx），这是刻意设计——
> 客户端看到 402 就重新走一遍支付流程即可，不需要区分具体原因。

### 7.3 关于超时

如果你卖的是大文件或需要现场生成的内容，交付可能耗时较长：

- 服务端的履约与连接脱钩，**客户端断开不会导致交付失败**；
- 客户端应把超时设长一些（例如 120 秒），并在超时后**用同一凭据重试**取回结果；
- 绝对不要在超时后**重新发起支付**。

## 8. 故障排查手册

### 8.1 启动阶段

| 现象 | 原因 | 处理 |
|---|---|---|
| `PrivateKey 是 PKCS#8 格式` | 密钥格式不对 | 用密钥工具「格式转换」转 PKCS#1 |
| `PrivateKey 不是合法的 Base64` | 混入了说明文字或多余换行 | 只保留纯 Base64 字符 |
| `ServerUrl 已指向生产网关，但 ServiceId 仍是 api_mock_service_id` | 生产网关配了沙箱 serviceId | 填入真实 serviceId |
| `SellerId 应为 2088 开头的商户 ID` | 填错了字段 | 填商户 PID，不是 APPID |
| 服务起不来，看日志找不到原因 | 日志位置不对 | systemd 配置里日志在 `/var/log/skillpay/app.log` |

### 8.2 支付阶段

| 现象 | 原因 | 处理 |
|---|---|---|
| 用户提示无法支付 | 三个单价不一致 | 见 4.3，逐一核对 |
| 付款后仍返回 402 | 本地订单校验未通过 | 查日志 `本地订单校验未通过`，看三个布尔值 |
| `amountMatches=False` | 账单金额与本地订单金额不符 | 检查是否有并发改价；确认三个单价一致 |
| `resourceMatches=False` | 资源标识不匹配 | 确认请求的 `skill_code` 与下账单时一致 |
| `orderUsable=False` | 订单查不到或已过期 | **检查部署脚本是否清空了 `appdata/`** |
| 验付返回 code 非 10000 | 支付宝侧拒绝 | 看日志里的 `subCode`，多为签约状态或 serviceId 问题 |

### 8.3 交付阶段

| 现象 | 原因 | 处理 |
|---|---|---|
| `履约准备失败` | 交付文件不存在 | 确认 `payloads/` 下文件确实存在，且路径大小写正确 |
| `超过内联上限` | 文件太大 | 提高 `MaxInlinePayloadBytes`，或改用外链交付 |
| 客户端超时但订单已付款 | 交付耗时超过客户端耐心 | **用同一凭据重试**，不要重新付款 |
| 交付内容与预期不符 | 交付物配错 | 查 `SkillCatalog` 里该资源的 `PayloadFile` |

### 8.4 一条通用排查路径

出问题时按这个顺序看，能覆盖 90% 的情况：

```
① GET /healthz            → 服务与数据库是否正常
② GET /                  → 资源目录与单价是否符合预期
③ 请求付费端点看 402      → 账单是否正常下发
④ 看服务端日志            → 有 outTradeNo 就能定位到具体订单
⑤ 查订单库                → 确认订单状态与履约状态
```

查订单库：

```bash
sqlite3 /opt/skillpay/app/appdata/skillpay.db \
  "select out_trade_no, order_status, fulfill_status, length(service_result) \
   from skillpay_orders order by rowid desc limit 5;"
```

## 附录 B：协议字段速查

### `Payment-Needed` 头（Base64URL 解码后）

```jsonc
{
  "protocol": {
    "out_trade_no": "SP20260917...",       // 商户订单号
    "amount": "29.90",                     // 金额（字符串，两位小数）
    "currency": "CNY",
    "resource_id": "skillpay:my-source-code",
    "pay_before": "2026-09-17T17:00:00+08:00",  // 支付截止时间
    "seller_signature": "...",             // RSA2 签名
    "seller_sign_type": "RSA2",
    "seller_unique_id": "2088..."
  },
  "method": {
    "seller_name": "...",                  // 账单展示的商户名
    "seller_id": "2088...",
    "seller_app_id": "2021...",
    "goods_name": "...",                   // 账单展示的商品名
    "seller_unique_id_key": "seller_id",
    "service_id": "..."
  }
}
```

### 签名原文

固定 8 个字段，按字典序，`k=v` 用 `&` 连接：

```
amount=29.90&currency=CNY&goods_name=...&out_trade_no=...&pay_before=...&resource_id=...&seller_id=...&service_id=...
```

> 取值位置：`goods_name`、`seller_id`、`service_id` 在 `method` 节点，其余在 `protocol` 节点。

### 200 响应

| 字段 | 说明 |
|---|---|
| `resource_id` | 资源标识 |
| `content` | **JSON 字符串**，交付物在此字符串内部 |
| `trade_no` | 支付宝交易号 |
| `out_trade_no` | 商户订单号 |
| `already_fulfilled` | 是否复用了既有产出 |
| `fulfillment_confirmed` | 履约是否已确认 |

### `Payment-Validation` 头

Base64URL 编码的回执，供调用方留痕对账：

```json
{
  "trade_no": "...",
  "out_trade_no": "...",
  "resource_id": "...",
  "validated": true
}
```

## 附：关于这份源码包的边界

**实现了什么**：HTTP 402 协议、账单签名、验付、幂等履约、订单持久化、资源交付（文本/文件）、
部署脚本、启动期配置校验、18 项联调断言。

**没实现什么**（按协议要求，也不应该加）：

- `notify_url` 异步通知——按量付费协议明确禁止混入
- 统一收单接口——与本协议无关
- 用户系统、退款流程——按量付费是「即付即交付」，退款请在支付宝商家后台处理

**已知限制**：

- 交付物以 Base64 内联，单次上限默认 8 MiB；更大的文件请改用对象存储外链
- SQLite 单文件数据库适合中小流量；高并发场景建议换成 PostgreSQL/MySQL
  （改 `Program.cs` 里的 `UseSqlite` 并替换 EF 提供程序即可，仓储层无需改动）
